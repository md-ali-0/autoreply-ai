# v1.52.6 — Hotfix: the provider key migration destroyed the keys it migrated

v1.52.5 shipped with a bug I introduced. It was found on the device, not by review, and
it cost the device's saved provider keys. This documents what happened precisely.

## What the device showed

After upgrading to v1.52.5, the AI test failed:

```
19:03:36  ✗ AI ব্যর্থ: HTTP 401 — {"error":{"message":"Missing ClientApiKey…"}}
```

A provider diagnostic added for exactly this situation then reported:

```
প্রোভাইডার ডায়াগনোসিস: প্রোফাইল 2 টা
  #1 xkiro · https://api.xkiro.com/v1 · id=44a2bd0f · key=নেই (খালি) · selected=true
  #2 tokenharbor · https://tokenharbor.ai/v1 · id=0eed6276 · key=নেই (খালি) · selected=false
প্রোভাইডার ডায়াগনোসিস: সিক্রেট নাম 0 টা —
```

**Zero secrets in secure storage.** But minutes earlier the migration had logged:

```
18:38:17  প্রোভাইডার key সুরক্ষিত স্টোরেজে সরানো হলো (id-তে 2 টা, প্লেইনটেক্সট মুছে 0 টা)
```

Two keys were migrated, and then every secret was gone. That contradiction is the bug.

## Root cause

Two defects that only combine into damage together.

**1. `fromJson` minted an id but did not persist it.** A profile written before `id`
existed has none in its JSON, so `fromJson` generated a UUID at read time. That UUID was
never written back to the list — so the *next* read minted a **different** one.

**2. `save()`'s orphan sweep then deleted the live key.** The sweep removes every secret
whose name is not in `live`, and `live` is built from the ids of the profiles it is
handed. Because the id changed between reads, the name holding the key was never the
name the sweep considered live.

The sequence on the device:

| Step | What happened |
|------|---------------|
| Boot 1 | Profile has no id → minted `X`. Legacy slot key found → written as `providerApiKey_X`, legacy name removed. **`X` never written to the JSON.** |
| (later) | A read mints `Y`. `get(providerApiKey_Y)` is null; the legacy slot name was already removed → key reads blank. |
| `save()` | `live = {providerApiKey_Y}`. `providerApiKey_X` is not in it → **deleted**. The only copy of the key is gone. |

So the migration succeeded, and then a later pass destroyed its own work. The log line
`id-তে 2 টা` was true when written and false by the time anyone read it.

## The fix

Persist the minted id **immediately**, before anything is stored under it:

```kotlin
var mintedIds = 0
for (i in 0 until arr.length()) {
    val o = arr.getJSONObject(i)
    val p = AiProvider.fromJson(o)
    profiles.add(p)
    legacyInline.add(o.optString("apiKey", ""))
    if (o.optString("id").isBlank()) {
        arr.getJSONObject(i).put("id", p.id)   // durable from this read onward
        mintedIds++
    }
}
if (mintedIds > 0) {
    try {
        sp(ctx).edit().putString(KEY_LIST, arr.toString()).apply()
        LogStore.add(ctx, "প্রোভাইডার পরিচয় বসানো হলো ($mintedIds টা)")
    } catch (e: Exception) {
        // If the id cannot be made durable, do NOT migrate under it — step 2 would
        // write the key into a name that is about to disappear.
        return profiles.mapIndexed { i, p -> p.copy(apiKey = legacyInline[i]) }
    }
}
```

The failure path matters as much as the happy one: if the id cannot be persisted, the
migration is abandoned for this read and the key is served from the legacy location. A
key that is not migrated is recoverable; a key migrated under an id that will not exist
next boot is not.

## Verification

`.verify/provider_store_check.py` — **40 assertions, all passing**, including four that
exist specifically for this regression:

- **14.** A profile with no id keeps the *same* id across reads, and the key still
  resolves on the second read.
- **15.** With the fix reverted, the id differs between reads and the second read cannot
  find the key.
- **16.** With `save()` in the loop, the orphan sweep destroys the only copy — the exact
  device symptom, reproduced.
- **17.** The fixed path survives `read → save → read` with the key and id intact.

Cases 15 and 16 are the *old* behaviour, kept so these assertions cannot pass vacuously.

Note on the harness: the buggy path had to be modelled with a genuinely **random** id.
An earlier version used a deterministic `ephemeral-{i}` and the bug did not reproduce —
a reminder that a stand-in for randomness has to actually be random, or it hides the
very race it is meant to show.

## Damage assessment — the keys on that device are gone

Not recoverable:

- `SecurePrefs` reports **0 secrets**.
- The legacy slot names (`providerApiKey_0`/`_1`) were removed by the migration's own
  adoption step, so there is no fallback copy.
- No cloud backup or exported snapshot for those providers exists on the device.
- The release build is not debuggable, so there is no `run-as` route to a stale copy.

The provider keys must be re-entered by hand on that handset. Two providers were
affected (`xkiro`, `tokenharbor`).

**This is the exact failure this whole thread of work was trying to prevent** — a key
silently disappearing with no error, discovered only when a reply never arrives. v1.52.5
wrote a new instance of it. Recorded plainly rather than smoothed over.

## Why review did not catch it

The 29 assertions in v1.52.5 all used profiles that **already had an id** — which is
what `save()` produces and what the fixtures naturally contained. The untested state was
"a profile that has a key but no id", i.e. precisely a real v1.52.4 install. The mirror
was faithful to the code and still missed it, because it shared the code's assumption
that ids exist.

The fix for that class of gap is the on-device seed hook
(`AiProviderStore.seedLegacyForTest` + the `providerseed` extra), which puts the store
into the pre-id state deliberately instead of relying on a fresh fixture to happen to
look like an upgrade.

## New diagnostics

Kept, because this was invisible without them:

- `--ez providercheck true` — logs each profile's resolved key as a length and a
  4-character fingerprint, plus the secure-store names present. Never logs a key.
- `--ez providerseed true` — puts one profile into the pre-id state with a known key.

## Device confirmation status

The fix is verified by the 40-assertion harness. On-device confirmation of the seed →
boot → boot → key-survives cycle was **interrupted**: the handset disconnected during the
run and has not reconnected. It must be re-run when the phone is available; until then
this fix is harness-verified only, and that distinction is deliberate — the harness
missing exactly this bug once already is the reason to say so.
