the priorities: **provider stable ID** (explicitly requested for this review) and the

## 1. Real-device process-death test — PASSED

### Why this needed hardware

`restorePending()` is the only thing standing between a queued reply and a contact
who is simply never answered. Source review can show the queue is written and read
back, but it cannot show that the file survives a process being killed outright —
no `onDestroy`, no final flush, only what was already on disk. `am force-stop` is the
harshest available version of that kill.

### Method

Two headless hooks were added, both going through **production code paths** rather
than writing fixtures by hand:

- `ReplyEngine.seedPendingForTest()` calls the real `enqueue()`, so the fixture is
  written by the same code that writes real entries and cannot drift from it.
- `ReplyEngine.pendingStateForTest()` returns `(inMemory, onDisk)` counts, so the
  failure that matters — "file still has it, memory does not" — is directly visible.

Driven from a workstation over adb:

```
adb shell am start -n com.claw.autoreplyai/.MainActivity --ez pendingtest true
adb shell am force-stop com.claw.autoreplyai
adb shell am start -n com.claw.autoreplyai/.MainActivity --ez pendingcheck true
```

### Result

Executed on the V2237 (Android 14). The clean, isolated single-entry run, reproduced
twice:

```
18:33:34  পেন্ডিং টেস্ট: কিউতে লেখা হলো          ← seeded 1 entry via enqueue()
          [am force-stop → pid 16868 dies, respawns as 17215]
18:33:37  বুটের পর সার্ভিস চালু হলো              ← fresh process, cold start
18:33:37  পেন্ডিং কিউ ফিরে এলো — 1 টা পাঠানো হবে   ← restorePending() re-armed 1
18:33:44  উত্তর দেওয়া হলো না (দরকার নেই) — PendingTest: process-death probe
                                                ← full reply pipeline ran on it
```

**1 in, 1 out, and the engine reached a reply decision.** The earlier run at 18:27
reported the same through the explicit check hook:

```
18:27:44  ✓✓ পেন্ডিং চেক সফল: প্রসেস মরে যাওয়ার পরও 1 টা ফিরে এসেছে
18:27:44  পেন্ডিং চেক: ডিস্কে 1 টা, মেমোরিতে 1 টা
```

After the queue drained, a subsequent check reported `ডিস্কে 0 টা, মেমোরিতে 0 টা` —
so the restore does not merely *load* the entry, it completes and clears it.

Evidence log: `docs/evidence/process-death-log-28sep.txt` (158 lines, five independent
kill/restore cycles captured).

### Two honest caveats

1. **The process came back on its own.** `KeepAliveService` is a
   `START_STICKY` foreground service, so `am force-stop` kills the process and Android
   restarts it ~2s later. This is not a weakened test — the process genuinely died with
   no `onDestroy` and no final flush, which is the property under test — but it does
   mean the "kill, then observe the file, then start manually" plan I originally
   intended is not possible on this device without disabling the service. I judged the
   auto-restart case to be the *more* realistic one anyway, since that is exactly what
   happens to a real user's phone: Android reclaims the app, the service brings it
   back, and the queue must survive.
2. **Delivery completed as an AI decision, not a physical WhatsApp send.** The probe
   message ("process-death probe") is synthetic, so the model returned an `IGNORE`
   decision — which is a correct end-to-end result and proves the pipeline ran, but it
   is not the same as a message appearing in a real chat. Proving that last hop
   additionally requires a real inbound message during the kill window, which is not
   scriptable without a second handset. I am flagging this rather than claiming more
   than the evidence shows.

## 2. Provider stable ID — implemented

### The problem, stated precisely

Provider keys are held in `SecurePrefs` under a *name*, and until now that name was
**the profile's position in the list** — `providerApiKey_0`, `providerApiKey_1`. That
made the name a lie the moment the list moved. Two consequences:

- Deleting or reordering a profile shifted the others down a slot, so every key had to
  be rewritten to follow the move. `save()` rewrote the entire key set on *every* write
  just to stay consistent.
- Any write that failed part-way through that renumbering left a key attached to the
  wrong profile — one provider authenticating as another.

I reproduced that failure in the harness rather than asserting it:

```
A and B migrate to providerApiKey_0 / providerApiKey_1.
A is then deleted, so B becomes the profile at index 0.
The old read resolves "the key for index 0" and gets KEY-A.
B now authenticates as A.
```

### What changed

`AiProvider` gained an `id` — a UUID, generated on creation, carried through
`toJson`/`fromJson`, and preserved across edits.

- **`secretName(id)`** replaces `secretName(index)`. A key is reachable from its own
  profile, not from wherever the profile sits in a list.
- **`save()`** touches only the profile that changed. There is nothing to renumber, so
  a partial failure can no longer misattribute a key. The orphan sweep enumerates the
  names actually present (`SecurePrefs.namesWithPrefix`) instead of walking a slot
  range, since ids are arbitrary strings with no "beyond the end" to walk to.
- **`rawList()`** resolves each profile's key in order: id-keyed secret → legacy
  slot-numbered secret → inline plaintext. The legacy slot name is adopted onto the id
  and then removed, so upgrading devices keep their keys.
- **`Backup.restore()`** matches by `id` first, falling back to name+endpoint for
  snapshots written before ids existed. On a match it adopts the local id as well as
  the key, so a restored profile points at the secret that actually exists.

### The bug this nearly introduced

`AiFragment.commitCurrentProvider()` rebuilt the profile from the on-screen text
fields **without passing `id`** — which, once `id` defaults to a fresh UUID, would mint
a new identity on every save and orphan the key that had just been written. The edit
would look fine, persist nothing, and the bot would silently stop authenticating. This
was caught by inspection of every `AiProvider(` construction site, not by the compiler,
and fixed by carrying `existing.id` across.

### Verification

`.verify/provider_store_check.py` — **29 assertions, all passing.** It mirrors the
store's exact logic (same fallback order, same per-profile scrub condition, same orphan
sweep) and covers:

- round trip; the list never holding an inline key
- delete and reorder leaving every survivor's key attached to the right profile
- adoption of a legacy slot-named secret onto the id
- legacy inline plaintext migrated then scrubbed
- **a failed Keystore write not scrubbing that profile's only copy** (the v1.52.4 bug
  class, re-tested against the id-keyed path), including the partial A/B/C case
- total Keystore failure losing nothing
- two profiles sharing a name and endpoint keeping distinct keys
- the old slot-keyed logic handing B the wrong key — kept live so the harness is not
  vacuous

Note on the harness: one assertion failed on the first run and **the test was wrong,
not the code** — I had run the old read twice against the same fixture, so its own
mutations polluted the second result. The fixture is now built fresh per branch.
