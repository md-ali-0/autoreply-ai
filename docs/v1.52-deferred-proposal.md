## 1. Room migration (reviewer's item #3)

### What the reviewer said
> SharedPreferences-as-database → Room.

### Why I did not do it
The actual access pattern is **"many small independent keyed blobs, each replaced whole"**:

| Data | Shape | Access |
|---|---|---|
| `chat_memory` | `Map<String, List<Turn>>` | read one bucket, write one bucket |
| `pending_replies` / `queue` | one JSON array | read whole, write whole |
| `last_reply` | `Map<String, Long>` | read key, write key |
| `sent_msgs` | bounded ring (32 conv) | read one, write one |

There is **no query** here. Nothing is filtered, joined, sorted, or aggregated. Room's value
is on the read-query side, and there is no read-query side.

More importantly: the v1.52 defect was **identity**, not the storage engine. The old code
keyed memory by `String.hashCode()` of a display name — that is broken in an SQLite table
exactly as badly as it is in SharedPreferences. **Moving to Room without fixing identity
would have shipped the same bug in a heavier container.**

And the migration itself is the risk: `restorePending()` reads the exact JSON field names
written by v1.51 (`sender`, `pkg`, `message`, `phoneHint`, `postTime`, `queuedAt`). Dropping
SharedPreferences means either a dual-read shim or an on-disk format change on a device you
depend on daily.

### What I recommend instead
Keep SharedPreferences. Harden what is actually missing:

- **`commit()` → `apply()` audit.** `pending_replies` must keep using `commit()` (synchronous,
  needed before process death). Everything else can be `apply()`.
- **A `storeVersion` key** so a future migration has a version to branch on — this is the
  cheap thing that makes a *later* Room move safe.
- **Thread-confinement audit:** every write already goes through `queueLock` for pending; add
  the same guarantee for `chat_memory`.

### If you still want Room
It is a **phased** job, not a rewrite: (a) add Room alongside, (b) dual-write for one
release, (c) dual-read with SharedPreferences as fallback, (d) cut over, (e) delete the old
path after a release of clean telemetry. Roughly 4× the work of the v1.52 commit, with a
real window where a bug loses history.

**Your call: keep SharedPreferences (recommended) or commission the phased move?**

## 2. Encrypted cloud backup (reviewer's item #6)

### What the reviewer said
> Encrypted cloud backup — the backup is plaintext.

### Current state after v1.52
`Prefs.exportJson()` now skips `apiKey`, `transcribeApiKey`, `cloudToken` — the keys are no
longer in the payload. But `AiProvider.toJson()` still serialises a provider's `apiKey`, so
**the backup is still not clean**. And the remaining payload (chat memory, contact allowlist,
reply history) is plaintext.

### Why this needs your decision — there is no free option
An encryption key must survive a **factory reset** for a backup to have any value. Three
possible sources, each with a different trade-off:

| Key source | Survives factory reset? | User burden | Verdict |
|---|---|---|---|
| Device-derived (Keystore, as in `SecurePrefs`) | **No** | none | Useless for a real backup |
| User passphrase | Yes | must remember a passphrase; lose it = lose backups | Works, honest |
| Server-held key (your cloud) | Yes | none | You now hold the keys to user chats |

That last row is the one I would **not** pick silently. Holding a server-side key means your
company can decrypt every user's chat memory — a materially different privacy posture, and a
different legal position, from "we can't read it".

### What I recommend
**User passphrase**, scoped to the backup only:
- `PBKDF2` (or Argon2 if you will accept the dependency) → AES-256-GCM, fresh salt per backup.
- The passphrase is **never stored**; the app asks when a backup is created and when one is
  restored.
- Cloud-backup screen gains one field and one honest warning line in Bangla:
  *"পাসওয়ার্ড ভুলে গেলে ব্যাকআপ আর খোলা যাবে না।"*

Also fix on the way: strip `AiProvider.apiKey` from the serialised payload — a provider's key
is user data too.

**Your call: passphrase (recommended), server-held key, or leave backups plaintext?**

## 3. P2 set — I can do these without a decision

These are implementation work, not judgement calls. Say the word and I will batch them.

| Item | What it means | Effort |
|---|---|---|
| **`AiProvider` stable ID** | providers are keyed by list index; reordering or deleting one silently reassigns another's config. Needs a UUID like `ConversationKey`. | small |

  interaction is intentional.

## 4. Blocking issue: device verification

**Nothing in v1.52 has been tested on hardware.** The phone dropped off USB mid-session.
The specific risks that cannot be reasoned away:

1. **R8 and the persisted `Pending` JSON.** Minification changed the class layout; the JSON
   round-trip (`sender`/`pkg`/`message`/`phoneHint`/`postTime`/`queuedAt`/`convPkg`/`convId`/
   `addr`) must be proven on a minified build, not a debug build.
2. **`ChatMemory.migrate()` under R8** — legacy `h_` key detection is reflection-adjacent.
3. **The `n:` / `m:` identity fallback** inside a real notification stream.
4. **The accessibility queue under two genuinely concurrent sends.**

Reconnect the phone when you can and I will run the same harness as v1.51: inject a
persisted queue into a release build, cold-start, confirm it drains; confirm legacy keys
migrate; fire two sends and confirm the FIFO holds.
