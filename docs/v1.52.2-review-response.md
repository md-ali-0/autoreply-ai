1. **Source inspection** — grep/read each named call site to confirm the claim is
   actually true in the shipped tree (`08938f5`), not merely plausible.
2. **Executable proof** — for the two fixes whose correctness is not obvious by
   reading, a mirror implementation was run against the same inputs:

     over 11 cases, including the reviewer's own example.

## What changed

### P0 — mood path now goes through the validator
`ReplyEngine.handle()`:
- The `shouldHoldBeforeReply()` gate was **hoisted above** the mood branch. Mood mode
  bypasses the contact filter and speaks *as* the user, so it needs the hold rule most,
  not least. An OTP request or a medical emergency can no longer be auto-answered.
- `handleMood()` now calls `ReplyValidator.validate(reply, message)` on the gatekeeper
  draft. A blocked draft is logged, recorded in memory, notified to the user and
  digested as `ACTION_HELD` — never sent.

### P0 — backup carries no credentials
- `AiProvider.toJson(includeSecret: Boolean = true)`; `apiKey` is only written when
  explicitly requested.
- `Backup.build()` passes `includeSecret = false`. The provider `apiKey` no longer
  escapes in the same file whose `settings` block already scrubbed its three secrets.
- Restore is unchanged in behaviour: it still honours an `apiKey` if an older snapshot
  contains one, so legacy backups restore with keys intact. New backups restore with a
  blank key that the user re-enters once.

### P1 — cloud backup is encrypted end to end
New `BackupCrypto`: PBKDF2-HMAC-SHA256 (120 000 iterations, 16-byte salt) → AES-256-GCM
with a fresh 12-byte IV per upload. Self-describing envelope
(`{enc, iter, salt, iv, ct}`), so an older plaintext backup is still readable and the
server never needs to know the format.

- `upload()` refuses to run with a blank passphrase rather than silently falling back
  to plaintext.
- `download()` decrypts → verifies → restores, in that order; a wrong passphrase aborts
  before anything local is touched.
- The passphrase is a normal preference, **not** `SecurePrefs` — deliberately. A backup
  whose key lives in this device's hardware is useless after the device is lost, which
  is the exact scenario the backup exists for.
- New settings field + explanatory note in `fragment_context.xml`.

### P1 — allow/block matching is exact
- `ReplyEngine.Matcher` replaces both `contains()` call sites.
- Names compare exactly (case-insensitively).
- A phone-number title compares **digits exactly**, so `+880 1321-329293`,
  `8801321329293` and `+8801321329293` are one person while `+88013213292930` is not.

### P1 — `ContactContext` keyed by `ConversationKey`
- `Entry` gains a nullable `key`; lookup prefers the key and falls back to an exact
  name match only for an entry that has no key yet.
- `adoptLegacy()` ties a legacy name-only entry to its conversation the first time that
  conversation is seen, then persists the key. Idempotent and failure-tolerant.
- Backup/restore carries the key, with `key` optional so older snapshots still parse.
- The settings screen keeps a typed name and now round-trips the key through the row.

### P1 — `ChatMemory` locking
- One lock per conversation bucket (`ConcurrentHashMap<String, Any>`), held across the
  whole load-append-write in `add()`. Scoped per conversation so a busy chat cannot
  stall an unrelated one.

### P2 — Base URL validation
- `AiClient.normalizeBaseUrl()` accepts a missing scheme, a trailing slash or a pasted
  full endpoint, and rejects whitespace, a non-http(s) scheme and a host with no dot
  (except `localhost`). Applied on every call, so a hand-edited or restored URL fails
  with a readable message instead of a raw socket error.

### P2 — bounded download
- `CloudBackup.readBounded(body, 16 MB)` replaces `body.string()` on the download path,
  throwing rather than silently truncating a half-read backup.

## Not done, and why

- **Room** — the reviewer withdrew this, and the recommendation is now a storage
  abstraction (`ConversationStore` / `PendingStore` / `ContextStore`). That remains a
  larger refactor and is not bundled into a fix release.
- **Provider stable ID (#7)** and **health/cooldown (#8)** — real gaps, acknowledged
  P2. Both are behavioural changes to provider selection: an ID migration has to
  preserve the selected-index semantics that `purgeBlocked`/`selectedIndex` depend on,
  and a cooldown needs a policy (how long, what counts as a failure) the user should
  choose rather than have chosen for them. Proposed for their own release.
